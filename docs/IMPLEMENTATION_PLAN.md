Phasing per spec §33/§44. Each phase ends with tests passing, types checked, and this plan updated with anything learned before moving on (§42).

## Home repositioned as a unified "What should I eat?" decision flow

Following a competitive analysis against Samsung Food (see the earlier landing-page note above), Home was reworked from three parallel mode buttons (Eat Now / Cook Today / Plan Ahead) — which just repeated the "which tool do I pick?" decision-fatigue problem the analysis flagged — into a single front door: **"What should I eat?"** plus six situational chips (Quick, Cheap, Filling, Family, Use what I have, Something different) and one "Ask FoodPadi" button, with the three tools demoted to secondary shortcuts underneath. This is a UX/routing change only — no new AI, no new engine, no rebuild of Eat Now/Cook Today/Plan Ahead's internals.

- `packages/shared/src/foodDecisionRouter.ts` — pure routing logic (`routeFoodDecision`), unit-tested (`foodDecisionRouter.spec.ts`, 8 cases covering every chip and combination). "Family"/"Use what I have" route to Cook Today's existing ingredient-picker screen (there's no honest way to answer them without real ingredient input, and building that would be pantry-scanning scope, explicitly out of bounds for this pass). Everything else becomes an Eat Now query; "Cheap" maps to the existing `maxPricePence` filter rather than a keyword (no catalog entry contains the literal word "cheap"). ✅ built and verified live end-to-end for both branches (Quick → Eat Now auto-search; Use what I have → Cook Today) plus the secondary shortcuts (Plan Ahead, direct Eat Now) still working unchanged.
- `EatNowService` gained a small "surprise me" fallback (`different`/`surprise`/`anything`/`variety` in the query bypasses keyword scoring and returns a shuffled sample instead of an empty result) — this is what makes the "Something different" chip and a chip-less "Ask FoodPadi" tap produce something useful rather than a dead end, without touching the normal (non-wildcard) empty-result behaviour.
- `EatNowScreen` now accepts optional route params (`initialQuery`, `initialMaxPricePence`, `whyLabel`) so it can be deep-linked into with a pre-built query and auto-run the search, showing a "Because you're after: …" line and capping results at 3 (vs. 5 for a manually typed search) — reusing the existing screen and endpoint rather than building a second results UI.
- Landing page (`apps/web`) copy was **not** updated to match this positioning yet — deliberately deferred since `apps/web` has substantial unrelated work in progress elsewhere with its own dev server running; revisit once that work is committed.

### Real location-aware "find it nearby" ✅ built and verified live with real results

Closes the "location permission flow, real source attribution" gap noted above — built to the user's detailed brief, kept as a supporting capability alongside the illustrative catalog search above, not a replacement (FoodPadi decides food, not restaurants — see [[foodpadi_decision_engine_architecture]]).

**Pivoted from Gemini + Google Maps grounding to the free OpenStreetMap stack (Nominatim + Overpass), no API key or billing at all.** The Gemini path was fully built and integration-tested first (current Interactions API, `google_maps` tool, structured JSON schema, cross-checking the model's claims against the tool's own raw place list before trusting anything) — but live testing surfaced a hard platform fact: Google Maps grounding has **no free tier at all**, confirmed directly (a `429` with zero billing, then a *different* `429` — "prepayment credits are depleted" — even after Cloud billing was correctly linked to the right project, because Gemini API billing runs on its own separate AI-Studio prepay balance). Given the user's explicit choice to stay free rather than prepay, the service was rebuilt on `apps/api/src/modules/local-food-search/local-food-search.service.ts`'s current implementation:

- **Nominatim** (`nominatim.openstreetmap.org/search`, UK-biased) geocodes the manual postcode/town fallback into coordinates; **Overpass** (`overpass-api.de/api/interpreter`) queries real nearby `amenity=restaurant/fast_food/cafe/pub/food_court` and `shop=chip_shop/bakery/deli` nodes within a radius. Both are free, keyless public services — a required `User-Agent` header is sent on every call per their usage policies.
- **No generative model in the loop at all for this feature** — arguably a stronger anti-hallucination story than the Gemini design it replaced, since there's nothing to hallucinate: matching is a deterministic curated keyword→OSM-tag map (`FOOD_SIGNALS`, same spirit as `eat-now-catalog.ts`) for `EXACT_MATCH`, falling back to a real-token-appears-in-the-real-tag check for a weaker `CLOSE_MATCH`; a business with neither is never shown. Every field (name/address/phone/website/distance) comes straight from that business's own OSM tags or is `null` — never guessed. Distance is a real haversine calculation from two real coordinates, not a model's assertion.
- One real bug found and fixed during live verification: the initial `nigerian`/`west_african`/**`african`** cuisine-tag signal for "jollof rice" matched an Egyptian restaurant (tagged with the broad continent-level `african` cuisine value) — too imprecise to count as real evidence of jollof rice specifically. Dropped the bare `african` tag from that signal; re-verified live and it now correctly surfaces only genuine Nigerian/West African restaurants (Enish, Akoko).
- Radius escalation (1mi → 3mi → 5mi) unchanged in spirit — retries the *same* Overpass query at a wider radius only if nothing survives the trust filter.
- No coordinates ever persisted/logged; `local_food_search_performed` analytics carries only `resultCount`/`radiusMetres`.
- Built on both platforms in one pass: web (`apps/web/app/eat-now/LocalFoodSearch.tsx`, browser Geolocation API) and mobile (`apps/mobile/src/components/LocalFoodSearch.tsx`, new `expo-location` dependency) — permission request → coordinates on success, manual postcode/town fallback on denial/failure/unsupported.
- Attribution: OpenStreetMap's ODbL license requires it, and the UI shows it plainly — "Results from OpenStreetMap · © OpenStreetMap contributors" (`LocalFoodSearchResponse.source: 'openstreetmap' | null`).
- ✅ **verified live with real results**, not just the graceful-failure paths: "fish and chips" near central London correctly returned Poppie's Fish and Chips and other genuine chip shops; "sushi" returned Wasabi/Tobiko/Abokado; "chicken biryani" returned Sagar/Colonel Saab/Arya Bhavan; the postcode-geocoding fallback ("SW1A 1AA") correctly resolved via Nominatim and found real nearby matches; close-match fallback sensibly surfaced J. Sheekey (a real seafood restaurant) for a fish & chips search it didn't exactly tag-match. Also verified live in a real browser end-to-end (query → manual location → real result cards with correct match badges, real phone/website/Maps links only where the underlying OSM data actually had them, honest attribution note).
- The public Overpass instance rate-limits rapid successive requests — this stopped being theoretical: a real user query ("beans") hit a `429` from `overpass-api.de` after the day's testing volume and surfaced as a plain "isn't set up yet" error. Fixed by trying two more public Overpass mirrors (`overpass.kumi.systems`, `overpass.openstreetmap.ru`) in sequence before failing, so one busy/rate-limited mirror no longer takes the whole feature down. ✅ verified live post-fix (the same "beans" query succeeded immediately after).
- `GEMINI_API_KEY`/`GEMINI_MODEL`/`@google/genai` are no longer used by this feature (dependency removed from `apps/api/package.json`) — left documented in `.env.example` in case a future pass revisits paid Gemini grounding for richer results (real menu items, opening hours, reviews) than OSM tags alone can offer.

## Phase 6 — Scan (photo scanning ✅ incl. demo mode, barcode not started)

Deliberately has **no curated fallback** in the real-AI path unlike Cook Today/Plan Ahead/Eat Now: a specific user's own photo can't be honestly faked with generic placeholder content, so real mode with no `ANTHROPIC_API_KEY` stays a plain 503 (verified: temporarily flipped `SCAN_DEMO_MODE=false` and confirmed the existing Anthropic gate is untouched and still reachable, then restored it).
- **`SCAN_DEMO_MODE`** (`apps/api/src/modules/scan/demo-scan-analyzer.ts`, enabled in this environment's `.env`): lets the whole Scan → Review → Pantry → Cook Today loop be validated with zero AI cost and no key. Three paths, same result shape either way (`{ items, demo }`): (1) an explicit "Try a sample kitchen" pick (4 deterministic scenarios — fridge/cupboard/mixed/shopping) always serves locally, regardless of the flag, since no real photo exists for those; (2) a real uploaded photo with the flag on is mapped to a scenario via a stable hash of the photo's own bytes (same photo → same result, never random, never sent to Anthropic); (3) a real photo with the flag off goes through the untouched real vision path. The review screen shows a small "Demo mode" tag when a result came from (1) or (2), never claiming AI involvement it didn't have.
- Review screen: checkbox include/exclude per item, an editable text field per item (in place, no separate edit mode), a ✕ to fully remove a row, and an "Add another item" input at the bottom (mirrors `ShoppingListScreen`'s existing pattern) — all before the single confirm button.

No new pantry-fetch endpoint was needed for this.
- ✅ built and verified live end-to-end through real browser interaction (not curl-only): registered an account, onboarded, opened Scan, picked "Sample fridge," removed one item, deselected another, edited "Milk" → "Oat milk," manually added "Butter," confirmed (5 items, matching the UI's own count), confirmed the `POST /pantry/items` network call, then followed "Cook with what's in your pantry" into Cook Today and confirmed via computed style that the two pantry items matching quick-add chips (Eggs, Tomatoes) were pre-selected and the other three (Oat milk, Chicken breast, Butter) appeared as custom chips.
- Analytics: reused the existing `AnalyticsService.track()` pattern for the two real backend actions (`scan_analysis_completed` with a `demo` flag, `scan_pantry_updated`). Pure client-side interaction events some specs might expect (e.g. "scan opened," "item removed" in the review UI) were deliberately **not** added — there is no existing generic client-event pipe for those (`FoodEvent`'s own doc comment is explicit that it's "derived from real domain actions... not a parallel tracking SDK"), and bolting one on for this pass would have been scope creep beyond what the analytics architecture already supports.
- Barcode scanning (deterministic lookup, no AI vision needed) — not started; no product/barcode data source chosen yet, same open question as Eat Now's data source.
- **Bug found and fixed live, on a real device**: every real photo (camera or library) failed with a generic "Something went wrong analysing that photo," even with `SCAN_DEMO_MODE=true`. Root cause was in `main.ts`, not Scan itself — Express's default JSON body-parser limit (100kb) silently rejected the request with `PayloadTooLargeError` before it ever reached `ScanController`, since `ImagePicker`'s `base64: true` photo (quality 0.7, no resize) inflates by ~33% on top of an already multi-MB phone photo. The 4 "Try a sample kitchen" demo buttons were unaffected (tiny payloads, no photo bytes), which is why those worked while every real photo silently failed. Fixed by raising the JSON/urlencoded body limit to 25mb in `main.ts` (`app.use(json({ limit: '25mb' }))`) — every other endpoint's payloads are trivially small by comparison, so this is a ceiling, not a behaviour change. ✅ verified live: a simulated 4MB base64 payload against the real `/scan/photo` endpoint now returns 201 with a demo scenario instead of a 413.
- Web equivalent — not built, per explicit MVP-focus direction; camera/photo capture is a mobile-native capability first, web would only support file upload.

## Unified decision engine (web) ✅ built and verified live — the intent-first entry point

Closes the concrete gap the [[foodpadi_decision_engine_architecture]] memory flagged: Home showed a mode-selection grid instead of a single "What should I eat?" entry point that decides for the user. A concurrent pass had already relabelled the three tiles as the "Understand Intent" branches (Right now / Cooking / Plan ahead) with a comment marking the "Understand Context" / "FoodPadi Decides" layer as not yet built — this closes exactly that.

- **`POST /decide`** (`apps/api/src/modules/decide`): given one free-text description of what the user has/wants plus optional soft constraints (`timeMinutes`, `budgetPence`), calls `CookTodayService.generate` and `EatNowService.search` **in parallel** (both exported from their modules for direct reuse — no new AI/recommendation logic, no duplicated engine) and blends the results toward 2 cook options + 1 get option (the exact shape from the architecture brief's own worked example — "1. Chicken fried rice, 2. Chicken rice bowl, 3. Get chicken & rice nearby"), topping up from whichever pool has more if one side is thin. Guest-accessible, same precedent as the two engines it blends.
- Each option carries a short, honest "why it fits" reason — `Ready in {N} min` for cook options (from the recipe's own `cookTimeMinutes`, not invented), `~{distance} mi · £{range}` for get options (Eat Now's existing illustrative estimates, already labelled as such elsewhere in the UI).
- **Location stays deferred until it's actually needed** — a direct, concrete instance of the architecture memory's "don't ask for location or hit a places API just because the user opened the decision flow" rule: the initial `/decide` call needs no location at all (Eat Now's catalog search doesn't use one); a location is only requested if the user picks "Get it" on a specific option, which reuses the existing `LocalFoodSearch` component seeded with that option's title as the query — the exact same component and backend built for Eat Now's own "find it nearby," not a duplicate.
- Web: `apps/web/app/DecideFlow.tsx` (new client component) — a single description input + optional time/budget fields + "Decide for me", rendering up to 3 option cards with a type badge (Cook it / Get it) and an inline expand: "Show recipe" reveals ingredients/steps for a cook option, "Find it nearby" mounts `LocalFoodSearch` for a get option. Mounted inside the existing `HomeHub` in `apps/web/app/page.tsx` — a minimal, additive edit (new import + one component call) rather than a rewrite, since that file had unrelated concurrent work in flight (a waitlist form, admin polish) that needed to stay intact; the stale "doesn't exist yet" comment above the three intent cards was also corrected to point here.
- ✅ verified live end-to-end in a real browser session: "something quick" correctly returned One-Pot Chicken & Rice (cook, 35 min) + Tomato & Basil Pasta (cook, 20 min) + Chicken shawarma wrap (get, ~0.4mi · £5-£7.50) — exactly 2-cook-1-get; "Show recipe" expanded real ingredients/steps inline; "Find it nearby" on the get option correctly seeded `LocalFoodSearch` with "Chicken shawarma wrap" and, via the manual-postcode path, returned real matching nearby businesses (Wrap It Up, Nando's) through the existing OSM-backed pipeline. A tighter time/budget constraint (20 min, £5) was also verified to correctly narrow the cook pool (`sanitizeRecipeCandidate` drops any candidate exceeding the requested time) down to just the options that actually fit — not a bug, the intended behaviour.
- Not built this pass: mobile port of the same unified entry point (mobile's Home still uses its own routing per `foodDecisionRouter.ts`); Plan Ahead is intentionally **not** blended into `/decide`'s 3-option output, since its own output shape (a multi-day plan + shopping list) is architecturally different from a single-moment decision, per the architecture memory's explicit note on this — it remains a direct secondary shortcut on Home, unchanged.

### Visual food images on recommendation cards ✅ built (needs `PEXELS_API_KEY` + migration to go live)

Turns the text-only Decide / Eat Now cards into a visual decision: each recommendation gets a small, representative photo of the dish so the customer can *see* what they're choosing (visual-redesign brief). Deliberately a supporting thumbnail, not a hero — brief §17.

- **`apps/api/src/modules/food-image`** — a provider-agnostic `FoodImageService`. `buildFoodImageQuery` normalises a dish name into a tight food-specific query (`"Chicken Biryani"` → `"chicken biryani indian food"`, with a small cuisine-hint map for culturally-ambiguous dishes — brief §28/§29, deterministic, no LLM call). `PexelsImageProvider` (preferred) then `UnsplashImageProvider` (fallback, dormant until `UNSPLASH_ACCESS_KEY` is set) are tried in order behind `pickBestPhoto`, a re-rank + reject pass over the top 8 results (reject people/venue/menu/low-res; rank by distinctive-word overlap with the dish name; fall back to the provider's own #1 when no alt text gives a signal). Small CDN renditions only (`src.medium` / `urls.small`), hotlinked per each provider's terms — nothing re-hosted. Keys are server-side only.
- **`FoodImageCache` model** (migration `20260830140000_add_food_image_cache`, **not yet applied** — needs `prisma migrate deploy` against Neon): one row per normalised dish name, so a provider is hit at most once per distinct dish, ever. Misses are cached too (`status = "none"`, 7-day TTL) so an image-less dish doesn't re-hit the provider every load.
- **Wired into**: `DecideService` (attaches an `image` to the final ~3 blended options only — not to Eat Now's up-to-12 matches on the decide path) and `EatNowService.search` (attaches to each result; `DecideService` opts out via `{ resolveImages: false }`). Both are best-effort — image resolution runs after the recommendation is built, behind a 4s per-provider timeout, and a failure just leaves `image` null. `DecisionOptionView` / `FoodIdeaView` gain an optional `image?: FoodImageView | null` in `@foodpadi/shared`.
- **UI**: new `FoodImage` component, web (`apps/web/components/FoodImage.tsx`) + mobile (`apps/mobile/src/components/FoodImage.tsx`) — compact fixed-height band (132/124px), shimmer skeleton while the photo loads, fade-in on load, subtle "Photo: … / Pexels" attribution beneath (brief §25). **No image found (or URL fails) ⇒ a shorter icon strip with a food glyph on a branded tint** — never a broken image, unrelated stock, or a big empty box (brief §15). Wired into `DecideFlow` (web + mobile) and the Eat Now search results (web `EatNowSearchForm`, mobile `EatNowScreen`).
- **Scope this pass**: Decide + Eat Now, web + mobile. Plan Ahead (per-meal images, lazy-loaded) deferred.
- **To go live**: add `PEXELS_API_KEY` (free key from pexels.com/api) to `apps/api/.env` + Render; run `prisma generate` and `prisma migrate deploy`. Until then every card just renders without a photo — nothing breaks.
